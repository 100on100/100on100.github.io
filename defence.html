In plain words

What 100on100 does, simply

Every dot is kept

Like packing crayons so carefully that none ever breaks: when you open the box, every crayon is exactly as it was.

For you: Every pixel the camera captured arrives exactly as it was taken.

A small program you can check

The program that opens the pictures is short, like a picture book instead of a phone book, so a grown-up can read every page.

For you: At about 27 KiB (code and data; its stack is reserved, not stored), your security team can review all of it, not trust a black box.

It says no to broken files

If a picture arrives broken, or someone has tampered with it, the program does not guess. It says “this one is broken” and gives the reason as a number.

For you: Crafted image files are a known way to attack computers. In our tests, every damaged or hostile file was either read exactly or turned away.

Same answer on every computer

Like a sum that gives the same answer on every calculator: it uses whole numbers only, so different machines cannot drift apart.

For you: Measured on laptop, ARM, RISC-V and browser chips: the same picture, so a receiver can prove it got what was sent.

Open just one piece

Like opening one page of a book without reading the whole book. The picture is cut into tiles, and you open only the tile you need. If one tile is damaged, the others still open.

For you: Send or decode just the region you care about over a narrow link.

Head to head

Smaller decoder. No undetected corruption.

For ISR data, a picture that is quietly wrong is worse than no picture. We damaged the same files the same ways for five codecs: 100on100 refused every one (version 4 files); the others let 0.3% to 75% through undetected. Its original version 4 C99 decoder (small build) is 9 to 79 times smaller than the JPEG-LS, JPEG 2000 and JPEG XL decoders.

100on100 checks a checksum over its header and over every tile, so any change to the data is caught and refused. CCSDS 121 streams and JPEG 2000 codestreams carry no integrity check over the coded data, by design; JPEG XL and JPEG-LS catch most damage through their own decoding, but not all.

Method: libjxl 0.11.2, OpenJPEG 2.5.4, CharLS 2.4.3 and libaec 1.1.6, each built from its release source the same way (size-optimised, unused code removed, runtime libraries not counted). 24 raw camera crops (CC0) encoded losslessly by every codec; each file then damaged 400 ways (one bit flipped, 4 octets overwritten, 16 octets zeroed, cut short), identically for every codec: 9,600 damaged files per codec, 48,000 in all. The problem

Large data, narrow links, fragile decoders

  • Raw frames are large and links are narrow, but analysis needs every bit.
  • Image decoders are large C and C++ libraries: a proven attack path, and the first code to touch data from outside.
  • Decoders that use floating point do not give identical output on different machines, so a hash of a decoded image proves nothing.

Raw, before colour

100on100 stores the sensor's own mosaic, before demosaicing, so nothing is interpolated away.

What you get

What 100on100 gives your programme

A decoder your team can review

27,272 octets: the whole RISC-V decoder image, code and data (stack and heap reserved, not stored), under a hard cap of 98,304. The original version 4 C99 library (small build), 9,075 octets of code and data, matches it byte for byte.

Hostile files turned away

A damaged or crafted file is refused with a numbered reason. In our tests, none became a plausible wrong picture.

One result on every machine

Integer-only decoding. A test stream gives one result on x86-64, ARM, RISC-V and WebAssembly, so a receiver can prove what it decoded.

Region decode

256 × 256 tiles. Decode only the region you need, or spread one frame across machines with identical results.
